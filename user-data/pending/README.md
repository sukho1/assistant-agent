# Pending 队列（延迟写入机制）

## 目的

让 trace / profile-update 真正不阻塞回复，而不是把"异步"当措辞。

## 机制

1. **回复发出前**：只向本目录写一个登记文件 `YYYY-MM-DD-主题.md`，内含：
   - 按精简模板写好的 trace 内容（≤30 行要点式）
   - profile 更新范围（哪几个文件、哪一层）
   此步几秒内完成，是回复前唯一允许的写入。
2. **下一次会话开始时**：flush——把登记文件移入 `user-data/trace/`，并按登记的更新范围执行 profile 写入。flush 完成后，本次回复才算完整落地。
3. 任何回复（A/B 类）开始前，先检查本目录：非空则先 flush，再处理新消息。

## 为什么不能"回复后立即写"

当前运行时中，最终回复发出即本轮结束，之后无法再执行工具。因此"异步补写"落实为"下次会话开头补写"。

## 权衡

- 若用户不再发消息，登记文件会一直保留在本目录，不丢失，下次会话自动补写。
- 若需要定时 flush（不等下次消息），需在 Codex 应用中配置线程唤醒/自动化。
- 登记文件即 trace 本体，flush 只是移动 + 执行 profile；内容在回复前已按模板备好，不依赖事后回忆。
